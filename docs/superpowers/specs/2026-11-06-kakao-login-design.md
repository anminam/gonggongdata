# 카카오 로그인 설계

작성일: 2026-11-06
함께 만드는 문서: `docs/superpowers/specs/2026-11-06-admin-settings-design.md` (관리자 설정 확장). 두 작업은 하나의 구현 계획으로 묶는다. *(사용자 결정)*

## 왜 하나

지금 로그인은 구글 하나뿐이다(`app/page.tsx`의 `signInWithOAuth({ provider: "google" })`).
국내 사용자에게 익숙한 카카오 계정으로도 가입할 수 있게 해서 가입 문턱을 낮춘다.

이 앱은 승인된 사용자에게 **메일로 알림을 보내는 것**이 핵심이다. 카카오는 사용자가 이메일 제공을 거부할 수 있으므로, 이메일이 없는 카카오 사용자에게는 **이메일을 입력하고 6자리 코드로 인증**하게 한다. *(사용자 결정)*

## 목표 / 하지 않을 것

**목표**
- 로그인 화면에 "카카오로 로그인" 버튼을 구글 버튼과 함께 둔다.
- 카카오가 이메일을 넘겨주면 그대로 쓴다. 구글 사용자와 똑같이 흘러간다.
- 이메일이 없으면, 다른 화면(승인 대기, 거절, 앱 본문)보다 **먼저 "알림 받을 이메일" 화면**을 보여 준다. 인증을 마쳐야 넘어간다.
- 인증된 이메일은 프로필 이메일이 되고, 기본 수신 주소로 등록되며, 가입 승인 방식(도메인 자동 승인 등)에도 쓰인다.

**하지 않을 것**
- 같은 사람의 구글·카카오 계정 합치기, 중복 계정 경고 표시. 관리자가 승인할 때 걸러낸다. *(사용자 결정)*
- 관리자 Gmail 발송 계정 연결 방식 변경 (구글 그대로)
- 가입 후 프로필 이메일 바꾸기 (수신 주소는 지금처럼 설정 화면에서 따로 관리)
- 다른 소셜 로그인(네이버 등)

**실패로 보는 것 (동작은 해도 안 됨)**
- 인증하지 않은 이메일이 프로필 이메일이나 수신 주소로 들어감
- 브라우저에서 값을 조작해 남의 이메일로 인증을 통과하거나, 인증 없이 프로필 이메일을 바꿈
- 이메일 인증을 이용해 도메인 자동 승인을 우회함 (인증 안 된 주소로 승인)
- 인증 코드가 DB나 화면, 로그에 그대로 노출됨
- 기존 구글 사용자의 로그인·승인 흐름이 바뀜

## 1. 로그인 화면

- `app/page.tsx` 로그인 영역에 "카카오로 로그인" 버튼을 추가한다. 구글 버튼 아래, 같은 크기.
- 버튼 색은 카카오 표준(노란 배경 `#FEE500`, 검은 글자, 말풍선 아이콘)을 따른다. *(내 판단: 카카오 디자인 가이드 권장)*
- 안내 문구 "Google 계정으로 로그인하세요."는 "Google 또는 카카오 계정으로 로그인하세요."로 바꾼다.
- 호출: `supabase.auth.signInWithOAuth({ provider: "kakao", options: { redirectTo: window.location.origin } })`.
  - 요청 범위(scope)는 Supabase 기본값을 쓴다. 이메일 동의가 '선택'이어도 로그인이 되도록 Supabase 쪽 설정이 필요할 수 있다 → 아래 "외부 설정" 참고.

## 2. 이메일 입력·인증 화면

**언제 보이나**
- 로그인했고, 프로필을 읽었고, `profile.email`이 비어 있으면(null 또는 빈 문자열) 이 화면을 보인다.
- 승인 대기·승인됨 상태보다 이 화면이 먼저다. 단, `rejected`면 지금처럼 거절 화면을 보인다. *(내 판단)*
- 구글 사용자는 늘 이메일이 있으므로 이 화면을 볼 일이 없다.

**흐름**
1. 이메일 입력 → "인증 코드 보내기"
2. 서버가 6자리 숫자 코드를 만들어 그 주소로 메일을 보낸다. 화면은 코드 입력 칸으로 바뀐다.
3. 코드 입력 → "확인"
4. 맞으면 서버가 프로필 이메일을 저장하고 승인 방식을 적용한다. 화면은 프로필을 다시 읽어 승인 대기 또는 앱 본문으로 넘어간다.

**화면 요소** — 기존 `Gate` + `Card` 모양(승인 대기 화면과 같은 틀). 새 디자인 요소는 만들지 않는다.
- 제목: "알림 받을 이메일을 알려 주세요"
- 설명: "카카오 계정에서 이메일을 받지 못했어요. 공지 알림을 받을 이메일을 인증해 주세요."
- 코드 단계: "OOO@OOO로 보낸 6자리 코드를 입력하세요", "코드 다시 보내기", "이메일 바꾸기"
- 로그아웃 버튼

**규칙** *(모두 내 판단)*
- 코드 유효시간 10분. 같은 코드로 틀릴 수 있는 횟수 5번, 넘으면 그 코드는 못 쓰고 새로 받아야 한다.
- 다시 보내기는 60초에 한 번. 새로 보내면 이전 코드는 못 쓴다.
- 한 사용자가 하루(24시간)에 보낼 수 있는 코드는 10번까지. (남의 주소로 메일 폭탄을 막기 위함)
- 이메일은 trim하고 소문자로 바꿔 저장한다. 형식 검사는 간단히(`@` 하나, 도메인에 `.`).
- 코드 메일 제목: `[공공데이터 알림] 이메일 인증 코드 123456`, 본문에 코드와 "10분 안에 입력하세요", "요청하지 않았다면 무시하세요". 기존 메일과 같은 흑백 톤.
- 발송은 기존 `sendMail()`(관리자가 연결한 Gmail 발송 계정)을 쓴다. 발송 계정이 연결되지 않았거나 발송이 실패하면 "인증 메일을 보내지 못했어요. 관리자에게 문의해 주세요."를 보인다.
- 관리자 설정의 "알림 메일 자동 발송 일시정지"와 상관없이 인증 메일은 나간다.

## 3. 서버와 DB

**API 라우트 2개** (`app/api/me/email/...`, 이름은 만드는 사람 판단)
- `send-code`: 로그인 확인(`userFromRequest`) → 프로필 이메일이 이미 있으면 거부 → 횟수·간격 확인 → 코드 생성 → **해시만** 저장 → 메일 발송.
  - 승인 대기(`pending`) 사용자도 호출할 수 있어야 한다. `rejected`는 거부한다. *(내 판단)*
- `verify`: 로그인 확인 → 코드 해시 비교(시간 일정 비교) → 맞으면 프로필 이메일 저장 + 승인 방식 적용 → 인증 기록 삭제.

**인증 기록 테이블** (예: `gd_email_verifications`)
- 사용자당 한 줄: user_id, 이메일, 코드 해시, 만료 시각, 틀린 횟수, 마지막 발송 시각, 24시간 발송 횟수 계산용 값.
- 코드는 평문으로 저장하지 않는다. 해시(예: 사용자 id와 코드를 섞은 SHA-256)만 저장한다.
- **RLS를 켜고 정책을 하나도 만들지 않는다** → 브라우저(anon, authenticated)는 읽기·쓰기 모두 불가. 서버만 service role로 다룬다. *(CLAUDE.md 보안 2번, 내 판단: 본인에게도 코드 해시를 보일 이유가 없음)*

**프로필 이메일 저장과 승인 적용**
- 지금 `gd_profiles` update는 관리자만 가능하다(RLS). 이 규칙은 그대로 두고, 서버가 service role로 바꾼다.
- 승인 방식 판단은 관리자 설정 설계와 같은 규칙을 **DB 함수 하나**로 묶어 가입 트리거와 이메일 인증이 함께 쓴다. *(내 판단: 규칙이 두 곳에 갈라지지 않게)*
  - 예: `gd_decide_status(email)` → `'approved'` 또는 `'pending'`. 관리자 고정 규칙(`minamhunmin@gmail.com`)도 이 함수 안에서 처리한다.
  - 이 함수는 service role에서만 실행 가능하게 한다(`revoke execute ... from public, anon, authenticated`). 트리거는 security definer라 그대로 부를 수 있다.
- 인증 성공 시 처리 (한 번에):
  - 프로필 `email`을 인증된 주소로 저장
  - 프로필 `status`가 `pending`일 때만 승인 방식을 적용해 `approved`로 바꿀 수 있다. `rejected`나 이미 `approved`는 건드리지 않는다.
  - 인증된 주소를 `gd_recipients`에 추가 (이미 있으면 무시). 지금의 기본 수신 주소 트리거는 프로필을 **처음 만들 때만** 동작하므로 여기서 직접 넣는다.
- 가입 트리거(`gd_profiles_before_insert`)는 지금처럼 `auth.users`의 이메일로 프로필 이메일을 덮어쓴다. 카카오가 이메일을 안 줬으면 null로 들어가고, 승인 방식은 이메일이 없으므로 `pending`이 된다(`all` 모드라도 이메일이 없으면 `pending`). *(내 판단: 이메일 없는 계정이 먼저 승인되지 않게)*

## 4. 관리자 화면

- 사용자 목록에서 이메일이 비어 있는 사용자는 이메일 자리에 "이메일 인증 전"을 보인다. *(내 판단: 빈칸으로 보이면 헷갈림)*
- 그 외 관리자 화면은 바꾸지 않는다.

## 5. 외부 설정 (사용자가 직접, 구현 후 안내)

코드는 키를 다루지 않는다. 키는 Supabase 대시보드에만 넣는다.
1. 카카오 개발자 콘솔에서 앱 만들기 → 카카오 로그인 켜기 → Redirect URI에 Supabase 콜백 주소(`https://<프로젝트>.supabase.co/auth/v1/callback`) 등록
2. 동의 항목: 닉네임·프로필 사진(선택), 카카오계정(이메일) — 비즈 앱이 아니면 '선택 동의'만 가능 **(확인 필요)**
3. REST API 키와 Client Secret을 Supabase 대시보드 > Authentication > Providers > Kakao에 등록
4. Supabase Kakao 설정에서 이메일 없는 사용자 허용 옵션 켜기 **(옵션 이름과 위치 확인 필요)**
5. 사이트 도메인(`https://gonggongdata.anminam.com`)을 카카오 앱 플랫폼(Web)에 등록

## 구현하면서 정한 것 (2026-11-06)

- 관리자 설정 확장은 다른 세션에서 먼저 끝났다. 카카오는 그 위에 따로 만들었다.
- 관리자 고정 규칙은 **구글 로그인에만** 적용한다. 카카오로 관리자 메일을 인증해도 일반 사용자다. *(추천안 적용)*
- 자동 승인은 **이메일을 인증하는 순간의 설정**으로 판단한다. *(추천안 적용)*
- 보안 수정: 기존 가입 트리거는 로그인 이메일이 없으면 브라우저가 보낸 이메일을 썼다. 그래서 카카오를 켜면 관리자 메일로 가장할 수 있었다. 이제는 `auth.users`의 **인증된** 이메일만 쓰고, 없으면 빈 문자열(`email` 컬럼은 not null)로 둔다.
- 승인 규칙은 `gd_auto_approve(email)` 하나로 모았다. 인증 성공 처리는 `gd_set_verified_email(user, email)` 하나로 묶었다. 둘 다 service role만 실행할 수 있다.
- 카카오 이메일 동의 항목(`account_email`)은 비즈 앱만 쓸 수 있다(Supabase 문서 확인). 그래서 대부분의 카카오 사용자는 이메일 인증 화면을 거친다.

## 확인 필요

- 카카오가 넘겨주는 이메일이 카카오에서 이미 인증된 주소인지, Supabase가 미인증 이메일을 어떻게 처리하는지. 미인증 이메일을 그대로 받는다면 그 주소도 우리 인증을 거쳐야 한다. → 구현 전 Supabase 문서로 확인하고, 확인되지 않으면 **카카오가 준 이메일도 신뢰하지 않고 인증 화면으로 보낸다**(안전한 쪽). *(내 판단)*
- 같은 이메일로 구글과 카카오에 가입했을 때 Supabase가 계정을 자동으로 합치는지. 합치든 안 합치든 이 설계의 동작은 바뀌지 않는다.

## 만드는 사람에게 맡기는 것

- API 라우트·테이블·함수 이름, 해시 방식의 세부
- 24시간 발송 횟수를 어떻게 셀지(컬럼 두 개 또는 시각 목록)
- 코드 메일 HTML의 세부 모양 (기존 메일 색 `MAIL_COLORS` 사용)
- 코드 생성·해시·검증 로직의 작은 테스트 위치 (`tests/` 아래, vitest)
