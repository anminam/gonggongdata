# 관리자 설정 확장 설계

작성일: 2026-11-06

## 왜 하나

설정 화면 맨 아래 "관리자 설정" 영역(관리자에게만 보임)에는 지금 "메일 발송 계정"만 있다.
코드에 박혀 있어서 바꾸려면 배포가 필요한 운영 값 세 가지를 관리자가 화면에서 바꿀 수 있게 한다.

1. 알림 메일 발송 일시정지
2. 가입 승인 방식
3. 알림 메일 제목 양식

## 목표 / 하지 않을 것

**목표**
- 세 설정을 설정 화면의 "관리자 설정" 영역에서 보고 바꾼다.
- 바꾼 값은 다음 자동 실행(매일 14:00 KST)이나 다음 가입부터 바로 적용된다. 재배포는 필요 없다.

**하지 않을 것**
- 수집 시각 변경 (vercel.json의 cron이라 화면에서 못 바꾼다)
- 메일 본문 문구 편집, 제목 양식 여러 개 저장해 고르기
- 수집 일시정지 (수집은 늘 돈다)

**실패로 보는 것 (동작은 해도 안 됨)**
- 일반 사용자가 설정을 읽거나 바꿀 수 있음
- 가입자가 브라우저에서 값을 조작해 스스로 승인됨
- 일시정지 중인데 자동 메일이 나감

## 1. 알림 메일 발송 일시정지 (사용자 결정: 수집은 계속, 발송만 멈춤)

- 스위치 하나: "알림 메일 자동 발송" 켬/끔. 기본은 켬.
- 끄면 `runDaily()`가 수집·저장은 그대로 하고, 3단계(사용자별 발송)만 건너뛴다.
  - 실행 기록(`gd_run_logs`)은 평소처럼 남기고, `emails_sent`는 0이다.
  - 실행 기록에 "발송 일시정지로 건너뜀"을 남길 방법(예: 기존 컬럼 활용 또는 컬럼 추가)은 만드는 사람 판단.
- 관리자 페이지의 "지금 실행"(`/api/admin/run`, 크론과 같은 `runDaily()`)도 일시정지 중에는 수집만 하고 발송하지 않는다. *(사용자 결정)*
- 강제 발송, 테스트 발송, 내 테스트 발송은 일시정지와 상관없이 그대로 동작한다. *(내 판단)*
- 다시 켜면: 지금 코드가 "최근 7일 중 아직 안 보낸 공지"를 보내므로, 멈춘 동안 쌓인 최근 7일 공지는 다음 자동 실행 때 나간다. 7일보다 오래된 건 안 나간다. 이 동작을 바꾸는 코드는 추가하지 않는다. *(내 판단)*
- 화면: 스위치 옆에 지금 상태를 보여 주고, 꺼져 있을 때는 "자동 알림 메일이 나가지 않아요. 수집은 계속돼요" 같은 안내를 보여 준다.

## 2. 가입 승인 방식 (사용자 결정: 세 가지 중 선택)

- 선택지: **수동 승인**(기본, 지금과 같음) / **도메인 자동 승인** / **전원 자동 승인**
- 도메인 자동 승인일 때는 허용 도메인 목록을 관리자가 넣고 뺀다 (예: `example.go.kr`).
  - 입력값은 앞의 `@`와 공백을 떼고 소문자로 저장한다.
  - 일치는 정확히 같은 도메인만으로 한다. 하위 도메인은 포함하지 않는다. *(내 판단)*
- 적용 시점: **새 가입(프로필 생성) 때만**. 이미 승인 대기 중인 사람을 한꺼번에 승인하지는 않는다. *(내 판단)*
- 자동 승인되면 `status = 'approved'`, `approved_at = now()`.
- 거절된 사람은 계정을 지우지 않고 `rejected` 상태로만 둔다. 그래서 다시 로그인해도 프로필이 이미 있어 재승인되지 않는다. 차단 목록은 만들지 않는다. *(사용자 결정)*

**보안 요구 (반드시)**
- 지금 프로필 줄은 브라우저가 만든다 (`app/page.tsx:59`의 insert). 그래서 승인 판단을 브라우저에 맡기면 안 된다.
- DB의 `BEFORE INSERT` 트리거(`security definer`)가 `gd_profiles`에 새 줄이 들어올 때 상태를 정한다.
  - 브라우저가 보낸 `status`, `approved_at`, `is_admin` 값은 무시하고 트리거가 덮어쓴다.
  - 도메인은 **`auth.users`에 있는 로그인 이메일**로 판단한다. 브라우저가 보낸 `email` 값으로 판단하지 않는다.
  - 같은 트리거에서 `gd_profiles.email`도 로그인 이메일로 덮어쓴다. 기존 `gd_add_default_recipient` 트리거가 이 값을 기본 수신 주소로 쓰므로, 남의 주소로 알림이 가는 것을 막는다. *(내 판단, 보안)*
- 계획 전에 Supabase에서 `gd_profiles`의 실제 컬럼, insert RLS 정책, `gd_is_admin()` 정의를 확인한다 (저장소의 `20261105_gd_init.sql`에는 설명만 있음).
- 기존 RLS가 이미 막고 있더라도, 트리거에서 다시 강제한다.

## 3. 알림 메일 제목 양식 (사용자 결정: 제목 전체 + 칸 넣기)

- 관리자가 제목 전체를 한 줄로 쓴다. 칸은 두 개만 쓴다.
  - `{건수}` → 이번 메일에 들어간 공지 수 (숫자만, 예: `3`)
  - `{날짜}` → 발송일 (한국 시간, `YYYY-MM-DD`)
- 기본값은 지금 제목과 똑같이: `🚨 공공데이터 API 변경공지 감지 {건수}건 ({날짜})`
- 비워 두면 기본값을 쓴다. 없는 칸(예: `{기관}`)은 글자 그대로 남는다.
- 테스트 발송일 때 앞에 붙는 `[테스트] `는 지금처럼 코드가 자동으로 붙인다.
- 줄바꿈은 저장할 때 공백으로 바꾼다 (메일 헤더 보호). 길이는 200자까지. *(내 판단)*
- 화면: 입력칸 아래에 쓸 수 있는 칸을 안내하고, 오늘 날짜와 예시 건수로 채운 미리보기를 보여 준다.
- 자동 발송, 강제 재발송, 테스트 발송 모두 이 양식을 쓴다 (`renderEmail` 한 곳에서 처리).

## 저장소와 권한

- 새 테이블 하나에 세 설정을 모은다. 한 줄짜리 설정 테이블(`id = 1` 고정, `gd_mail_sender`와 같은 방식). 이름은 예: `gd_app_settings`.
  - 들어갈 값: 발송 일시정지 여부, 승인 방식, 허용 도메인 목록, 제목 양식, 수정 시각, 수정한 관리자
- **RLS를 켜고**, 읽기와 쓰기 모두 관리자만 허용한다 (기존 `public.gd_is_admin()` 사용).
- 서버(크론, 발송)는 service role로 읽는다.
- 가입 트리거는 `security definer`라서 RLS와 상관없이 읽는다.
- 줄이 없으면 위의 기본값으로 동작한다 (발송 켬, 수동 승인, 기본 제목).
- 마이그레이션 파일은 `supabase/migrations/`에 기존 이름 규칙(`YYYYMMDD_gd_...sql`)으로 추가한다.

## 화면

- 설정 화면의 "관리자 설정" 영역(`app/components/Settings.tsx`)에서 기존 "메일 발송 계정" 카드 옆과 아래에 카드 세 개를 더한다.
  - 알림 메일 발송, 가입 승인 방식, 알림 메일 제목
- 기존 `SectionCard`, `Switch`, `ToggleGroup`(또는 `Select`), `Input`, `Button`을 쓴다. 새 디자인 요소는 만들지 않는다.
- 저장 성공이나 실패는 기존 방식(토스트)으로 알린다.

## 만드는 사람에게 맡기는 것

- 테이블과 컬럼 이름, 도메인 목록을 배열 컬럼으로 둘지 별도 테이블로 둘지
- 화면은 브라우저에서 RLS로 바로 읽고 쓸지, `/api/admin/...` 라우트를 거칠지 (둘 다 관리자 확인은 필수)
- 제목 칸 치환과 도메인 정규화의 작은 테스트 위치
