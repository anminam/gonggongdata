# 공공데이터 API 공지 알림 서비스 설계 (전체)

작성일: 2026-11-06
성격: **지금 구현된 서비스 전체를 기준으로 처음부터 다시 쓴 정리본.** 이 문서만 읽고 같은 서비스를 다시 만들 수 있게 쓴다.
이전 부분 설계(`2026-11-06-admin-settings-design.md`, `2026-11-06-kakao-login-design.md`)의 내용은 모두 이 문서에 합쳤고, 두 문서는 지웠다(git 기록에 남아 있음).
기준 환경: 지금 운영 중인 Supabase 프로젝트(anminam-edu)와 그 데이터를 그대로 쓴다. 새 프로젝트로 옮기는 일은 이 문서의 범위가 아니다(옮긴다면 17장 2번, 그리고 `gd_deliveries`를 함께 옮겨야 최근 7일 공지가 다시 나가지 않는다).

표기: *(사용자 결정)* 은 사용자가 정한 것, *(내 판단)* 은 만들면서 정한 것, **확인 필요** 는 아직 검증하지 않은 것.

## 1. 무엇이고 왜 하나

공공데이터포털(data.go.kr)의 **API 공지사항**(점검, 제공 중단, URL 변경, 규격 변경 등)은 API를 쓰는 사람에게 중요하지만, 사이트에 직접 들어가 봐야 알 수 있다.
이 서비스는 공지를 **매일 오후 2시(KST)** 에 자동으로 모으고, 사용자가 정한 조건(키워드, 기관, 공지 유형)에 걸리는 공지만 **메일 한 통으로 묶어** 보낸다.

- 주소: https://gonggongdata.anminam.com
- 사용자: 관리자가 승인한 사람만 쓴다 (기관 내부·지인 대상의 작은 서비스).
- 관리자: 한 명(고정 이메일의 구글 계정). 승인, 수집 실행, 발송 계정 연결, 운영 설정을 맡는다.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것

**목표**
- 하루 한 번 새 공지를 빠짐없이 모으고, 조건에 걸린 공지를 사용자별로 한 번만 보낸다.
- 사용자는 화면에서 조건을 바꾸면서 "어떤 공지가 걸리는지" 바로 확인할 수 있다.
- 관리자는 배포 없이 화면에서 운영 값(발송 일시정지, 가입 승인 방식, 메일 제목)을 바꾼다.

**하지 않을 것**
- 실시간 알림, 푸시, 카카오톡 알림 (메일만)
- 수집 시각을 화면에서 바꾸기 (Vercel cron 고정)
- 메일 본문 문구 편집, 제목 양식 여러 개
- 구글·카카오 계정 합치기, 네이버 등 다른 소셜 로그인
- 가입 후 프로필 이메일 바꾸기 (수신 주소는 따로 관리)
- 공지 원문 전체 보관·검색 엔진 (본문은 8000자까지만)

**실패로 보는 것 (동작은 해도 안 됨)**
- 승인되지 않은 사람이 공지나 다른 사람 데이터를 읽음
- 일반 사용자가 관리자 설정을 읽거나 바꿈, 또는 브라우저 값을 조작해 스스로 승인됨
- 인증하지 않은 이메일이 프로필 이메일·수신 주소·자동 승인 판단에 쓰임
- 같은 공지가 같은 사용자에게 자동 발송으로 두 번 나감
- 발송 일시정지 중인데 자동 메일이 나감
- 비밀 키(서비스 키, Gmail refresh token, 인증 코드)가 브라우저나 로그에 노출됨

## 4. 하루 동작 (수집 → 저장 → 발송)

`runDaily()` (`lib/run.ts`) 하나가 전부 한다. 매일 Vercel cron(`0 5 * * *` UTC = 14:00 KST)이 `/api/cron/crawl`을 부르고, 관리자의 "지금 실행"도 같은 함수를 부른다. 서버 실행 시간은 60초.

1. **실행 기록 시작**: `gd_run_logs`에 `running` 줄을 만든다.
2. **새 공지 목록 모으기** (`collectFreshNotices`)
   - 목록 주소: `selectNoticeListView.do?nttApiYn=Y&pageIndex=N&pageUnit=30&searchOrder=REGIST_DT` (최신순 30건)
   - 1페이지부터 읽다가 **이미 저장된 공지가 하나라도 나오거나**, 30건보다 적으면 멈춘다. 최대 3페이지(60초 제한). *(내 판단: 하루 30건 넘게 올라와도 놓치지 않게)*
   - 각 줄에서 공지 id(`fn_view('...')`), 번호, 기관명, 제목, API명, 등록일을 뽑는다.
   - 1페이지에서 한 건도 못 뽑으면 "페이지 구조 변경 가능성" 오류로 실패시킨다.
3. **새 공지 저장**: 새 공지마다 상세 페이지(`selectNotice.do?originId=...`)의 본문을 읽는다. 본문은 "URL 복사하기" 뒤부터 "목록으로 돌아가기" 앞까지, 끝의 "API 목록"은 잘라내고 8000자까지만 둔다. 상세를 못 읽어도 본문을 비운 채 저장한다. 유형(`notice_type`)은 저장할 때 분류해 둔다. `gd_notices`에 upsert.
4. **사용자별 발송** — 관리자 설정 `mail_paused`가 켜져 있으면 이 단계 전체를 건너뛴다.
   - 대상: `approved` 사용자 전원. 사용자마다:
     - 알림 받기를 껐으면 건너뜀
     - 조건(키워드·구독 기관)이 하나도 없으면 건너뜀
     - 수신 주소가 없으면 건너뜀
     - **최근 7일**(등록일 기준) 공지 중 조건에 걸리고, `gd_deliveries`에 아직 없는 공지만 고른다
     - 하나라도 있으면 메일 **한 통**으로 묶어 그 사용자의 모든 수신 주소로 보내고, 공지마다 `gd_deliveries`에 기록(걸린 이유, 받은 주소, 보낸 시각)
   - 최근 7일을 보는 이유: 키워드를 새로 추가한 사람도 지난 일주일 공지는 받게. *(내 판단)*
5. **실행 기록 끝**: 성공이면 `success`, 새 공지 수, 보낸 메일 수. 실패면 `error`와 오류 문구. 결과로 `{ ok, newNotices, emailsSent, mailPaused }`를 돌려준다.

**보내기와 기록의 순서**: 메일을 **먼저 보내고 그다음 기록**한다. 그래서 메일은 나갔는데 기록 저장이 실패하면 다음 실행 때 같은 공지가 다시 나갈 수 있다(빠지는 것보다 중복이 낫다는 쪽). *(지금 구현 그대로)*

**한 사용자 발송이 실패하면?** 지금은 자동 발송에서 예외가 나면 실행 전체가 `error`로 끝난다(뒤 사용자는 못 받음). 관리자 수동 발송들은 사용자별로 잡아서 "실패: …"로 결과에 남긴다. → **확인 필요**: 자동 발송도 사용자별로 잡을지.

## 5. 공지 분류 (`lib/classify.ts`)

규칙 기반. 제목에서 먼저 찾고, 없으면 본문에서 찾는다. **순서가 중요**하다 (점검성 "일시 중단"이 "중단"보다 먼저).

| 순서 | 유형 | 걸리는 말(요약) | 영향 / 조치 |
|---|---|---|---|
| 1 | 일시 중단(점검) | 점검, 정전, 순단, 패치, 이용 불가, 일시 중단, 작업으로 | 점검 시간 동안 이용 불가 / 장애 모니터링 |
| 2 | 제공 중단/종료 | 제공·서비스 중단/종료, 폐기, 폐지, 중단 안내, 종료 안내 | 제공 종료 예정 / 대체 API 전환 검토 |
| 3 | URL 변경 | URL·주소·도메인 변경, 엔드포인트 | 기존 URL 종료 예정 / 신규 URL 전환 검토 |
| 4 | API 변경 | 변경, 개편, 전환, 버전, 파라미터, 필수, 규격 | 요청/응답 규격 변경 / 연동 수정 검토 |
| 5 | 신규/추가 | 신규, 추가, 오픈, 개방 | 신규 기능·데이터 / 활용 검토 |
| - | 기타 | 위에 없음 | 내용 확인 필요 / 원문 확인 |

- 본문에 "변경 후 URL … https://…"가 있으면 그 주소를 "신규 URL"로 뽑고, API 변경이었으면 URL 변경으로 바꾼다.
- 본문에 "N일 유지/병행"이 있으면 영향에 "(기존 N일 유지 후 중단)"을 덧붙인다.
- 화면(공지 상세)과 메일이 같은 함수를 쓴다.

## 6. 알림 조건과 매칭 (`lib/match.ts`)

서버 발송과 화면 미리보기가 **같은 함수**로 매칭한다.

- **키워드**: 제목 + API명 + 기관명(+ "본문까지 검사"를 켜면 본문)에 키워드가 들어 있으면 걸림. 대소문자 무시, 부분 일치, 여러 키워드는 OR. 키워드는 1~100자.
- **구독 기관**: 공지 기관명이 **정확히 같으면** 걸림. 걸린 이유는 `기관:OO`로 남긴다.
- **받을 유형**: 고른 유형의 공지만 받는다. 저장 값 `null` = 모든 유형(앞으로 생길 유형 포함). 유형이 비어 있는 공지는 "기타"로 본다.
- 최종: (키워드 OR 구독 기관) AND 받을 유형.
- 키워드와 구독 기관이 둘 다 없으면 아무 메일도 가지 않는다.

## 7. 알림 메일 (`lib/mailer.ts`)

- **제목**: 관리자 설정의 제목 양식(아래 11장). 기본 `🚨 공공데이터 API 변경공지 감지 {건수}건 ({날짜})`. 테스트 발송은 앞에 `[테스트] `.
- **본문**: 텍스트 버전과 HTML 버전을 함께 보낸다. HTML은 메일 프로그램 호환을 위해 표 + 인라인 스타일, 화면과 같은 흑백 톤.
  - 머리말: 발송 계정을 연결한 관리자의 프로필(동물) 이미지. 없으면 🔔.
  - 유형별 건수 요약
  - 공지 카드마다: 유형 배지, 제목, 기관, API, 공지일, 영향, 조치, (신규 URL), 알림 이유(키워드·기관 칩), [공지 원문 보기] 버튼
- **보내는 사람**: `"공공데이터 공지 알림" <연결된 Gmail 주소>`. 받는 사람은 그 사용자의 수신 주소 전부(한 통).
- **발송 방식**: `gd_mail_sender`의 refresh token으로 Google 토큰을 받아 Gmail API `messages/send`로 보낸다. 모든 외부 호출 타임아웃 15초. 서버리스에서 SMTP 연결이 멈추는 문제 때문에 HTTPS를 쓴다. *(내 판단)*
- 발송 계정이 연결되지 않았으면 "연결된 Gmail 발송 계정이 없습니다…" 오류.

## 8. 로그인과 가입

### 8.1 로그인 화면
- 로그인 전 첫 화면: 왼쪽에 소개("공공데이터포털 공지, 이제 놓치지 마세요." + 기능 3개), 오른쪽에 [Google로 로그인], [카카오로 로그인] (카카오 노란 `#FEE500`), "처음 로그인하면 관리자 승인 후 이용" 안내.
- 세션을 확인하기 전에는 스피너만 보인다.

### 8.2 프로필 만들기
- 로그인 후 `gd_profiles`에 내 줄이 없으면 브라우저가 `insert({ user_id, email })`를 한다.
- **승인 판단은 브라우저를 믿지 않는다.** DB의 `BEFORE INSERT` 트리거 `gd_profiles_before_insert()`(security definer)가 값을 정한다.
  - 프로필 이메일 = `auth.users`의 **인증된** 이메일. 없으면 빈 문자열. 브라우저가 보낸 email은 절대 쓰지 않는다.
  - 구글 로그인 + 관리자 고정 이메일 → `approved`, `is_admin = true`
  - 그 밖에 `gd_auto_approve(이메일)`이 참 → `approved` (11장의 가입 승인 방식)
  - 아니면 `pending`. `is_admin`은 항상 `false`.
- `AFTER INSERT` 트리거 두 개: 기본 알림 설정 줄 만들기(`gd_user_settings`), 프로필 이메일이 있으면 기본 수신 주소로 등록(`gd_recipients`).
- 프로필을 못 읽으면 세션을 한 번 새로 고친 뒤 다시 읽고, 그래도 안 되면 "프로필을 불러오지 못했어요" + [다시 시도][로그아웃]. 로딩·오류가 "승인 대기"로 잘못 보이지 않게 상태를 따로 둔다.

### 8.3 이메일 인증 (주로 카카오) *(사용자 결정: 이메일 없는 가입자는 6자리 코드로 인증)*
카카오 이메일 동의 항목은 비즈 앱만 쓸 수 있어서, 대부분의 카카오 가입자는 이메일 없이 들어온다.
- **언제**: 프로필 이메일이 비어 있고 `rejected`가 아니면, 승인 여부와 상관없이 이 화면이 먼저 나온다.
- **흐름**: 이메일 입력 → `POST /api/me/email/send-code` → 6자리 코드 메일 → 코드 입력 → `POST /api/me/email/verify` → 성공하면 프로필을 다시 읽어 다음 화면으로.
- **규칙** *(내 판단)*
  - 코드 유효 10분, 틀릴 수 있는 횟수 5번
  - 다시 보내기 60초 간격, 24시간에 10번까지 (남의 주소로 메일 폭탄 방지)
  - 이메일은 trim + 소문자, 254자 이하, 간단한 형식 검사
  - 코드는 평문 저장 금지. `sha256(사용자id:코드)`만 저장하고, 비교는 시간 일정 비교. (shortcut: 소금 없는 해시. 표가 service role 전용이라 충분, 표가 공개되면 HMAC로)
  - 인증 메일은 발송 일시정지와 상관없이 나간다
- **인증 성공 처리**: DB 함수 `gd_set_verified_email(user, email)` 하나로 한 번에
  - 프로필 이메일 저장 (이메일이 비어 있고 `rejected`가 아닌 프로필만)
  - `pending`이면 그 순간의 승인 방식으로 자동 승인 판단
  - 수신 주소 등록, 인증 기록 삭제
- 관리자 고정 규칙은 **구글 로그인에만** 적용한다. 카카오로 관리자 메일을 인증해도 일반 사용자다.

### 8.4 승인 대기·거절 화면
- `pending`: "관리자 승인 대기 중", `rejected`: "승인이 거절되었어요 … 관리자에게 문의". 둘 다 이메일 표시와 [새로고침][로그아웃].
- 거절된 사람은 계정을 지우지 않고 `rejected`로 둔다. 다시 로그인해도 프로필이 있으니 재승인되지 않는다. *(사용자 결정)*

## 9. 사용자 화면 (승인된 사용자)

공통 틀: 왼쪽 사이드바(접으면 아이콘만), 위쪽 헤더(메뉴 버튼, "공공데이터 알림 / 현재 화면", 테마 전환). 화면 틀은 `fixed inset-0`으로 고정하고 본문만 스크롤한다(태블릿 크롬 주소창이 접힐 때 메뉴가 밀리는 문제). 모바일에서는 메뉴를 누르면 사이드바가 닫힌다.

사이드바 메뉴: **대시보드, 공지 목록, 알림 설정, 발송 이력** (+ 관리자만 **관리자**). 공지 목록 옆에 공지 수, 알림 설정 옆에 조건 수 배지.
아래 계정 메뉴: 프로필 이미지, 이메일, 역할 / 설정, 프로필 이미지 변경, 테마(라이트·다크·시스템), 로그아웃.

앱이 열리면 공지(최신 1000건)와 내 키워드·구독 기관·알림 설정을 한 번 읽어 모든 화면이 함께 쓴다.

### 9.1 대시보드
- 숫자 카드 4개: 저장된 공지(+ 마지막 수집 시각), 최근 7일 공지, 내 알림에 걸린 공지, 내가 받은 알림
- 차트: 최근 30일 일별 공지 수, 최근 30일 유형별 공지 수(막대를 누르면 그 유형으로 걸러진 공지 목록으로)
- 내 알림에 걸린 최근 공지 6건 + [전체 보기](내 조건만 켠 공지 목록)
- 조건이 없으면 [알림 설정하기] 안내

### 9.2 공지 목록
- 거르기: 검색(제목·기관·API명), 유형, 기관(건수 많은 순), 기간(7일/30일/전체), "내 알림 조건만"
- 50건씩 [더 보기]. 거르기를 바꾸면 다시 50건부터.
- 줄을 누르면 옆 패널에 상세: 유형·영향·조치·신규 URL, 내 알림에 걸린 이유, 수집 시각, 원문 링크, 본문

### 9.3 알림 설정
- **키워드**: 입력 후 Enter로 추가(한글 조합 중 Enter 무시), 삭제. 키워드마다 지금 걸리는 공지 수. 입력하는 동안 "이 키워드면 N건 걸려요" 미리보기 5건.
- **추천 키워드**: 저장된 공지의 제목·API명·기관명에서 2번 이상 나온 말을 많이 나온 순으로 20개(흔한 말과 조사로 끝나는 말 제외, 이미 추가한 것 제외). 처음 10개, [더보기]로 펼침. 누르면 바로 추가.
- **구독 기관**: 공지에 나온 기관을 건수순으로 보여 주고 체크로 구독. 목록에 없는 이름도 구독 가능(정확히 같은 이름일 때만 걸린다는 안내).
- **받을 유형**: [전체](null 저장), [중요한 것만](제공 중단/종료, URL 변경, API 변경), 유형별 체크와 건수·비율. 전부 고르면 null로 저장. 하나도 안 고르면 "메일이 하나도 가지 않아요" 경고.
- **수신 주소**: 추가·삭제. 0개면 경고와 [로그인 메일로 받기].
- **옵션**: 알림 받기, 본문까지 키워드 검사, [테스트 메일 보내기]
- **조건별 최근 매칭**: 키워드·기관마다 가장 최근에 걸린 공지 1건

### 9.4 발송 이력
- 내가 받은 기록(최근 500건): 공지, 유형, 걸린 이유, 받은 주소, 보낸 시각. 검색 가능.
- 숫자: 보낸 공지 수, 보낸 메일 수(같은 사용자·같은 분이면 1통), 마지막 발송, "매일 14:00 한국 시간"
- 관리자는 [내 이력 / 전체 사용자] 탭으로 모든 사용자 기록을 볼 수 있다.

### 9.5 설정 (계정 메뉴에서)
- 모두: 프로필(이미지·이메일·역할), 화면 테마, 알림 받기, 수신 주소
- 관리자만 (아래 "관리자 설정" 영역): 메일 발송 계정 + 11장의 카드 3개
- 프로필 이미지는 동물 그림 20개 중 고르고, Supabase 로그인 정보(`user_metadata.gd_avatar`)에 저장한다(테이블 아님).

## 10. 관리자 화면

- **숫자 카드**: 승인된 사용자, 승인 대기, 마지막 실행(성공/실패/실행 중), 발송 계정(연결됨/미연결)
- **[지금 크롤링 실행]**: `runDaily()`. 발송 일시정지 중이면 결과에 "메일은 보내지 않았어요".
- **발송 계정 연결**: 미연결이면 경고와 [Gmail 발송 계정 연결]. 관리자 구글 계정으로 `gmail.send` 권한(오프라인, 매번 동의)을 받아, 돌아온 refresh token을 서버가 `gd_mail_sender`에 저장한다. 토큰은 화면으로 다시 내려보내지 않는다.
- **승인 대기 목록**: [수락]/[거절]. 이메일이 없으면 "이메일 인증 전".
- **사용자 표**: 승인된 일반 사용자는 [차단](rejected), 거절된 사용자는 [승인].
- **실행 기록**: 최근 20회 (시작, 결과, 신규 공지, 메일 수, 오류)
- **강제 발송**: 승인된 사용자를 골라(최대 50명) 세 가지 중 하나. 각 사용자 줄에 "계정 → 받는 곳"을 보여 주고, 수신 주소가 없으면 "안 보내져요". 결과는 사용자별 "k건 보냄" 또는 이유.

| 버튼 | 무엇을 | 기록 | 알림 꺼진 사람 | 확인 창 |
|---|---|---|---|---|
| 테스트 발송 | 그 사람 조건에 걸린 최근 7일 공지(최대 10건, 없으면 최신 1건 샘플)를 `[테스트]` 제목으로 | 안 남김 | 보냄 | 없음 |
| 다시 보내기 | 최근 7일 걸린 공지를 이미 보낸 것까지 다시 | 시각만 갱신 | 보냄 | 있음 |
| 이 공지 보내기 | 검색해서 고른 공지 1건을 조건과 상관없이 | 남김(이유가 없으면 "(관리자 발송)") | 보냄 | 있음 |

## 11. 관리자 설정 (배포 없이 바꾸는 운영 값)

한 줄짜리 테이블 `gd_app_settings`(id = 1). 줄이 없거나 값이 null이면 기본값으로 동작한다. 바꾼 값은 다음 실행·다음 가입부터 바로 적용된다.

### 11.1 알림 메일 자동 발송 *(사용자 결정: 수집은 계속, 발송만 멈춤)*
- 스위치 "자동 발송"(저장 값 `mail_paused`, 기본 false = 켬).
- 끄면 자동 실행과 "지금 실행" 모두 수집·저장만 하고 사용자별 발송을 건너뛴다. 실행 기록은 남고 메일 수는 0.
- 관리자 강제 발송 3종, 사용자 테스트 메일, 이메일 인증 메일은 일시정지와 상관없이 나간다. *(내 판단)*
- 다시 켜면 최근 7일 중 못 보낸 공지가 다음 실행 때 나간다. 7일보다 오래된 건 안 나간다. 꺼져 있을 때 화면에 이 안내를 보여 준다.

### 11.2 가입 승인 방식 *(사용자 결정: 세 가지)*
- **수동 승인**(기본) / **도메인 자동 승인** / **전원 자동 승인**
- 도메인 목록: 입력값은 앞 `@`와 공백을 떼고 소문자, 점이 있어야 함. 정확히 같은 도메인만(하위 도메인 제외). 비어 있으면 아무도 자동 승인되지 않는다. *(내 판단)*
- 판단은 DB 함수 `gd_auto_approve(이메일)` 한 곳. 인증된 이메일만 넘어오므로, 남의 도메인 주소로 승인받을 수 없다. 이메일이 없으면 전원 자동 승인이어도 `pending`.
- 새 가입(또는 이메일 인증 성공) 때만 적용. 이미 대기 중인 사람을 한꺼번에 승인하지 않는다. *(내 판단)*

### 11.3 알림 메일 제목 *(사용자 결정: 제목 전체 + 칸 두 개)*
- 칸: `{건수}`(이번 메일의 공지 수), `{날짜}`(발송일, KST `YYYY-MM-DD`). 모르는 칸은 글자 그대로.
- 비우면 기본 제목. 줄바꿈은 공백으로, 200자까지(DB에도 제약).
- 화면에 오늘 날짜·예시 3건으로 채운 미리보기. 자동·강제·테스트 모든 메일이 같은 양식을 쓴다.

화면은 API 없이 브라우저에서 바로 읽고 쓴다. 관리자인지는 RLS가 확인한다. 저장하면 토스트, 실패하면 화면 값을 되돌린다.

## 12. 데이터 (Supabase, 모든 표 RLS 켬)

`gd_is_approved()` = 내 프로필이 approved, `gd_is_admin()` = approved이면서 is_admin. 둘 다 security definer.

| 표 | 내용 | 브라우저 권한 (RLS) |
|---|---|---|
| `gd_profiles` | user_id, email(not null), status(pending/approved/rejected), is_admin, approved_at, created_at | 읽기: 본인 또는 관리자 / 만들기: 본인 줄만(값은 트리거가 덮어씀) / 고치기: 관리자만 |
| `gd_user_settings` | user_id, enabled(기본 true), search_body(기본 false), notify_types(null=전체), updated_at | 승인된 본인만 모두 |
| `gd_keywords` | user_id, keyword(1~100자), (user_id, keyword) 유일 | 승인된 본인만 모두 |
| `gd_org_subscriptions` | user_id, org(1~200자), (user_id, org) 유일 | 승인된 본인만 모두 |
| `gd_recipients` | user_id, email(형식 검사), (user_id, email) 유일 | 승인된 본인만 모두 + 관리자 읽기 |
| `gd_notices` | notice_id(키), seq_no, org, title, api_names, registered_at(date), body, url, notice_type, crawled_at | 승인된 사용자 읽기만 |
| `gd_deliveries` | user_id, notice_id, matched_keywords, recipients, sent_at, (user_id, notice_id) 유일 | 본인 또는 관리자 읽기만 |
| `gd_run_logs` | started_at, finished_at, status(running/success/error), new_notices, emails_sent, error | 관리자 읽기만 |
| `gd_mail_sender` | id=1, email, refresh_token, connected_by, updated_at | **없음** (서버 전용) |
| `gd_app_settings` | id=1, mail_paused, approval_mode, approval_domains[], subject_template, updated_at, updated_by | 관리자만 읽기·만들기·고치기 |
| `gd_email_verifications` | user_id(키), email, code_hash, expires_at, attempts, sent_at, window_start, window_count | **없음** (서버 전용) |

- 사용자·공지가 지워지면 딸린 줄(키워드, 구독, 수신 주소, 발송 기록)도 함께 지워진다.
- 서버(크론, 발송, 인증)는 service role 키로 RLS를 우회한다. 이 키는 서버 코드에서만 쓴다.
- DB 함수 `gd_auto_approve`, `gd_set_verified_email`, `gd_add_default_recipient`는 브라우저(anon, authenticated)가 실행할 수 없다.
- 마이그레이션은 `supabase/migrations/YYYYMMDD_gd_...sql`. 첫 마이그레이션(`20261105_gd_init.sql`)은 설명만 있고 실제 SQL은 Supabase 대시보드에 있다. → **확인 필요**: 새 프로젝트에 다시 만들 수 있게 init SQL을 저장소로 옮길지.

## 13. API 라우트

모두 `force-dynamic`. 사용자 확인은 `Authorization: Bearer <Supabase access token>` → 서버가 토큰으로 사용자를 찾고 프로필을 읽는다.

| 경로 | 누가 | 하는 일 |
|---|---|---|
| `GET /api/cron/crawl` | `Bearer CRON_SECRET` | `runDaily()` (60초) |
| `POST /api/admin/run` | 관리자 | `runDaily()` (60초) |
| `GET /api/admin/gmail` | 관리자 | 연결된 발송 계정 이메일·시각 (토큰 제외) |
| `POST /api/admin/gmail` | 관리자 | refresh token 저장 |
| `POST /api/admin/test-send` | 관리자 | 테스트 발송 (user_ids 1~50개, UUID 검사) |
| `POST /api/admin/resend` | 관리자 | 다시 보내기 (같은 검사) |
| `POST /api/admin/send-notice` | 관리자 | 공지 1건 보내기 (notice_id 100자 이하 + 같은 검사) |
| `POST /api/me/test-send` | 승인된 사용자 | 내 조건으로 `[테스트]` 메일 (최대 10건, 기록 없음) |
| `POST /api/me/email/send-code` | 로그인 사용자(이메일 없음, 거절 아님) | 인증 코드 발송 (간격·횟수 제한, 실패 시 502) |
| `POST /api/me/email/verify` | 같음 | 코드 확인, 성공 시 `gd_set_verified_email` |

관리자 발송 결과는 사용자별 `{ user_id, email, status: sent|skipped, count, reason? }`. 이유 문구: 알림 꺼짐, 알림 조건 없음, 수신 주소 없음, 새 공지 없음, 최근 7일 걸린 공지 없음, 저장된 공지 없음, 실패: ….

## 14. 화면 공통 규칙

- 한국어, 한국 시간(`Asia/Seoul`) 표시. 날짜 비교는 `YYYY-MM-DD` 문자열.
- 흑백 미니멀 테마(+ 인디고 포인트), Noto Sans KR, 라이트/다크/시스템. 흑백이라 유형 배지는 채움·테두리와 아이콘으로 구분한다.
- 결과 알림은 화면 위 가운데 토스트. 오래 걸리는 작업은 "진행 중" 토스트를 결과로 바꿔 끼운다.
- 중복 입력은 DB 유일 제약 오류를 받아 "이미 있는 …예요"로 바꿔 보여 준다.
- 로딩은 뼈대(Skeleton), 빈 화면에는 다음에 할 일을 안내한다.
- 카카오톡 공유 미리보기용 OG 이미지(1200×630, 검정 배경)와 메타.
- 기존 shadcn 컴포넌트만 쓰고 새 디자인 요소는 만들지 않는다.

- 실사이트(`npm run test:live`): data.go.kr 목록·상세 파싱 (읽기만, DB·메일 없음). CI에서는 실패해도 전체를 막지 않는다.
- CI: GitHub Actions에서 타입 체크 + 단위 테스트 + 실사이트 테스트

## 16. 보안 정리

- 비밀 키는 `.env`(gitignore)와 Vercel·Supabase 대시보드에만.
- 승인·관리자 여부·프로필 이메일은 DB 트리거와 함수가 정한다. 브라우저가 보낸 값은 믿지 않는다.
- 브라우저에서 직접 쓰는 곳(승인 상태 변경, 관리자 설정, 키워드, 수신 주소 등)은 권한이 RLS에만 달려 있다. 표를 새로 만들면 반드시 RLS와 정책을 같이 만든다.
- 서버 전용 표(`gd_mail_sender`, `gd_email_verifications`)는 RLS를 켜고 정책을 두지 않는다.
- 관리자 고정 이메일은 DB 트리거 안에 있고(값은 `20261106_gd_kakao_email_verify.sql`에 있음), 구글 로그인일 때만 통한다. 관리자를 바꾸려면 트리거를 고치는 마이그레이션이 필요하다.

## 17. 확인 필요 (아직 검증·결정되지 않은 것)

1. 자동 발송 중 한 사용자 메일이 실패하면 실행 전체가 멈춘다. 사용자별로 잡고 계속할지.
2. 첫 마이그레이션 SQL이 저장소에 없다. 다시 만들 수 있게 옮길지.
3. 일시정지 → 재개 흐름은 단위 테스트로만 확인했다. 실제 운영에서 한 번 돌려 보지 않았다.
4. 카카오가 이메일을 넘겨주는 경우(비즈 앱) 그 이메일이 Supabase에서 "인증됨"으로 들어오는지.
5. 같은 이메일로 구글·카카오에 가입했을 때 Supabase가 계정을 합치는지 (합치든 안 합치든 동작은 같음).
6. 수집이 60초 안에 끝나지 않을 만큼 새 공지가 많은 날(최대 3페이지, 90건)의 동작. 수집과 발송이 한 번의 60초 실행에 들어 있어서, 사용자가 늘면 넘칠 수 있다. Vercel 요금제(Hobby/Pro)에 따라 대응이 달라진다.
7. Gmail 발송용 Google OAuth 앱이 "게시(프로덕션)" 상태인지. "테스트" 상태면 refresh token이 7일 뒤 만료되어 자동 발송이 실패한다. 지금은 만료를 따로 알려 주지 않고, 실행 기록의 오류로만 보인다.
8. 메일 발송 후 기록 저장이 실패하면 중복 발송이 생길 수 있다(4장). 이대로 둘지.
